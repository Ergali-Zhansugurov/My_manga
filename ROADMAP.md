# Roadmap — My_manga

Платформа для чтения манги/манхвы/ранобе + отдельная «студия», где авторы новелл находят художников и вместе выпускают тайтлы.

Проект учебный: цель — изучить и реализовать на достойном уровне микросервисы, авторизацию с ролями, RabbitMQ, Kafka, векторный поиск, юнит-тесты и фронт. Правило: **в работу идёт только то, что реально нужно; остальное — в «Later»**.

Легенда: `[MVP]` — обязательно для первой рабочей версии, `[Later]` — отложено.

## Архитектура (целевая)

```
                  ┌──────────┐
   Browser ──────▶│   web    │  (frontend)
                  └────┬─────┘
                       │ REST + JWT
     ┌─────────────────┼──────────────────┬───────────────────┐
     ▼                 ▼                  ▼                   ▼
┌─────────┐     ┌────────────┐     ┌────────────┐      ┌────────────┐
│  auth   │     │  content   │     │ discovery  │      │  studio    │ [Later]
│ users,  │     │ manga,     │     │ поиск,     │      │ питчи,     │
│ roles,  │     │ chapters,  │     │ vector     │      │ коллабы,   │
│ JWT     │     │ pages,     │     │ search,    │      │ публикация │
└─────────┘     │ community  │     │ read-model │      └────────────┘
                └─────┬──────┘     └─────▲──────┘
                      │ outbox           │
                      ▼                  │
                 ┌─────────┐   events    │          ┌──────────┐
                 │  Kafka  │─────────────┴─────────▶│ billing  │ [Later]
                 └─────────┘                        └──────────┘
                      │
                 ┌──────────┐   jobs    ┌──────────┐
                 │ RabbitMQ │──────────▶│ workers  │ уведомления, обработка картинок
                 └──────────┘           └──────────┘
```

### Сервисы

| Сервис | Отвечает за | Своя БД | Этап |
|---|---|---|---|
| **auth** | регистрация, логин, JWT (access + refresh), роли | `users`, `user_profiles`, `refresh_tokens` | MVP |
| **content** | источник правды по тайтлам: Manga, Ranobe, Chapter, Page, Author, Genre, Format, ScanlationTeam + комменты, рейтинги, закладки, история | основная схема из курсовой | MVP |
| **discovery** | поиск (full-text + векторный), каталог «имя / ссылка / обложка», топы | read-model + pgvector | MVP |
| **notifier** (worker) | рассылка уведомлений (новая глава в закладках и т.п.) | `notifications` | MVP |
| **studio** | отдельный сайт для авторов: питчи сюжетов, отклики художников, команды, публикация в content | своя схема | Later |
| **billing** | подписки, покупка глав, донаты, выплаты авторам | `subscriptions`, `payments`, `donations`, `payouts` | Later |

**Почему именно так, а не мельче:** каждый новый сервис — это отдельный деплой, конфиг, миграции и контракт. Комменты, рейтинги и закладки завязаны на тайтлы и главы, поэтому остаются в `content`, пока не появится реальная причина их вынести.

### Роли (auth)

Глобальная роль у пользователя одна:

| Роль | Кто | Может |
|---|---|---|
| `reader` | все зарегистрированные | читать, комментировать, оценивать, закладки |
| `creator` | авторы, переводчики, художники, все кто заливает работы | + создавать/редактировать свои тайтлы и главы, состоять в командах |
| `admin` | только ты | всё + модерация, выдача ролей |

Роль внутри команды (`translator`, `editor`, `cleaner`, `typesetter`, `proofreader`, `team_lead`) остаётся в `TeamMember`: это **права на ресурс**, а не глобальная роль. Отсюда вывод: в курсовой роль `translator` у `User` надо заменить на `creator`.

### Две очереди и зачем каждая

Главный принцип: **RabbitMQ — «сделай эту работу один раз и надёжно», Kafka — «вот что произошло, читайте все, кому интересно, в том числе заново»**.

**Kafka — поток доменных событий** (`chapter.published`, `manga.created/updated`, `rating.changed`, `chapter.read`)
- Одно событие читают несколько независимых потребителей: discovery (переиндексация), notifier (кому слать), статистика популярности, инвалидация кэша (то, что уже начато в `cache_broker.go`).
- Лог хранится, поэтому можно **переиграть** события и пересобрать поисковый индекс или эмбеддинги с нуля. RabbitMQ так не умеет.
- Порядок внутри тайтла сохраняется, если ключ партиции = `manga_id`.
- Публикация через **transactional outbox**: событие пишется в ту же транзакцию, что и данные, поэтому не теряется.

**RabbitMQ — очередь задач**
- `image.process`: после загрузки страниц пережать в webp, сделать превью и обложки. Тяжёлая работа, её надо раздать воркерам и выполнить ровно один раз.
- `notification.send`: доставить конкретное уведомление конкретному юзеру.
- Здесь нужны ack, ретраи с задержкой и **DLQ** для упавших задач. У RabbitMQ это есть из коробки, а в Kafka пришлось бы городить вручную.

Связка: `chapter.published` (Kafka) → notifier определяет, кого уведомить → кладёт N задач `notification.send` в RabbitMQ.

### Репозитории

Рекомендация: **монорепо** на старте (`services/*`, `web/`, `deploy/`, `pkg/`) + `go.work`. Проще рефакторить контракты, пока они не устоялись. Выносить в отдельную репу стоит только `studio`, если он станет отдельным продуктом, и то не раньше этапа 8.

## Принятые решения
1. **Монетизация:** правило «N читателей», комиссии и доли пока не формализуем, это пет-проект. Разберёмся на этапе 9.
2. **Эмбеддинги:** только локальная модель. Сначала векторизуем название, жанры и описание. Позже добавим комментарии и текст ранобе, чтобы искать тайтл по абстрактному описанию идеи или «вайба».
3. **Фронт:** Vue.
4. **Контент:** на старте остаются и сканлейт, и оригиналы. Потом смещаемся к оригинальному контенту из studio и лицензированию.
5. **Схема БД:** меняем свободно. Курсовая — отправная точка, а не контракт.

## Порядок работы
1. `main`: README + ROADMAP + приведение репо в порядок (этап 0).
2. Ветка под MVP: ТЗ (`docs/spec.md`) → доменная модель → интерфейсы → тесты → реализация.
3. На каждое значимое архитектурное решение — короткий ADR в `docs/adr/`.

Тестирование:
- бизнес-логика — юнит-тесты (table-driven, моки репозиториев);
- репозитории и миграции — интеграционные тесты на реальном Postgres (testcontainers).
